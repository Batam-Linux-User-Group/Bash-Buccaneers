CHAPTER 01SYSTEM FOUNDATION

1. The Linux Kernel: Architecture, System Calls, and Rings

In August 1991, Finnish student Linus Torvalds announced on Usenet that he was building a free, hobby-scale operating system for 386/486 PCs. What emerged was a Unix-like core that runs at the most privileged level of the hardware.

Monolithic Architecture vs. Microkernel Design

Unlike microkernels such as Mach or MINIX, which delegate file systems, memory management, and drivers to separate user-space servers, Linux is a monolithic kernel. Every primary subsystem runs in one address space at Ring 0, which avoids the overhead of message passing. To stay flexible, Linux uses Loadable Kernel Modules (LKMs), so drivers and filesystems can be added to the running kernel without a reboot.

System Calls: The Boundary Barrier

When an application needs to read a file, open a network socket, or create a process, it cannot touch hardware directly. It issues a system call (such as open() or write()) that traps the CPU into Ring 0. The kernel verifies the request, performs it, and returns the result across the boundary.

CHAPTER 02INTEGRATION

2. Distributions: Assembling the Integrated OS

A standalone kernel cannot boot an interactive environment by itself. A distribution supplies the rest: a tested, coherent assembly of the pieces that turn the kernel into a usable operating system.

GNU / Userland Toolchain

Core POSIX utilities (coreutils, bash, grep, sed) and the C library (glibc or musl) form the userland most scripts expect. Alpine swaps in musl and BusyBox for a smaller footprint.

Init Daemon & PID 1

The kernel hands control to PID 1, usually systemd, with OpenRC, runit, and s6 as common alternatives. It mounts filesystems, starts services, and supervises daemons.

Display Server Protocol

The graphical stack is Wayland or X11. Modern desktops default to Wayland for tear-free rendering and better app isolation, with X11 kept as a fallback.

Default Configuration

Distros ship opinions: default shell, kernel parameters, firewall rules, and update policy. Two distros on the same kernel can behave very differently.

CHAPTER 03GRAPHICAL LAYER

3. Desktop Environments: Modularity and Interface Paradigms

In proprietary systems the visual shell is inseparable from the kernel. In Linux, the interface is a swappable layer: a user can run a headless server with no display stack at all, or pick a desktop that matches their workflow and hardware.

GNOME 40+

GTK 4 / Mutter

A distraction-free, gesture-driven workflow with a single overview for windows and apps. Opinionated by design and extended through shell extensions.

Footprint: moderate

KDE Plasma 6

Qt 6 / KWin

Extremely configurable, with a traditional panel layout and deep control over themes, widgets, and window behavior.

Footprint: moderate

XFCE

GTK 3 / Xfwm

A stable, lightweight desktop that favors simplicity and low resource use. A common pick for older hardware.

Footprint: light

Tiling Compositors

Sway / Hyprland

For power users: windows tile automatically and everything is driven by the keyboard and a text config file.

Footprint: very light

CHAPTER 04SOFTWARE DELIVERY

4. Package Managers: Software Delivery & Isolation

Linux software has long been delivered through central repositories instead of downloaded installers. Packages are cryptographically signed, and the manager resolves dependencies for you.

APTAPT (Advanced Package Tool)

Debian, Ubuntu, Mint

Uses the .deb archive format. Highly conservative dependency resolution suits systems that value stability.

DNFDNF / Zypper

Fedora, RHEL, openSUSE

Employs the RPM format together with a SAT solver for dependency resolution, plus transaction history that makes rollbacks practical.

PACPacman

Arch, EndeavourOS, Manjaro

Rolling-release manager built around simple tar.zst archives. Fast, minimal, and paired with the community-run AUR.

EBDPortage (Source-Based)

Gentoo

Compiles software from source using ebuild recipes and USE flags, so you choose exactly which features are built in.

The Modern Paradigm: Sandboxed Runtimes (Flatpak & Snap)

Universal formats bundle an app with its dependencies and run it in a sandbox, so one build works across distributions and apps cannot freely read the rest of the system.

FLATPAK / OSTREE

Community-driven, distributed through Flathub, with per-app permissions.

SNAP / SQUASHFS

Canonical's format, served from the Snap Store and used for both desktop and server apps.
